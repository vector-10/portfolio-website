## The problem

On flaky mobile networks, a payment request would time out client-side and get retried — but the original request had often already reached the server and completed. The result: duplicate charges, discovered by customers, not by monitoring.

## The decision

Every payment request now carries a client-generated idempotency key. On receipt, the server takes a row-level lock on that key in Postgres before doing any payment processing. If a request with the same key arrives while the first is still in flight, or after it's completed, it resolves to the original transaction's result instead of processing a new charge.

The lock — not just a lookup-then-insert check — is what makes this safe under concurrent retries. A plain "check if key exists, then insert" has a race window; two near-simultaneous retries can both pass the check before either has inserted. Row-level locking closes that window.

## The outcome

Duplicate-charge incidents from retried requests dropped to zero across staging load tests that simulated exactly this failure mode — burst retries against the same payment within a few hundred milliseconds of each other.

## What I'd change

The idempotency key currently has no expiry, so the table grows unbounded. A time-boxed key (e.g. valid for 24 hours) would be enough for real-world retry windows, while keeping the table size in check without added complexity.
