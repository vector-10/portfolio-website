## Current state

Recurring billing and settlement jobs run on cron, on a single instance. If that instance goes down mid-run, or two instances end up running simultaneously during a deploy, jobs either silently skip a cycle or run twice.

## Proposal

Move job scheduling to a distributed scheduler with leader election: only one worker holds the lock to run a given job at a time, and if that worker dies mid-job, another worker picks up leadership and resumes on the next tick.

## What this closes off

- Duplicate job runs during deploys or scaling events
- Silent skipped runs when the single cron instance is unhealthy
- No visibility into whether a scheduled job actually ran — the scheduler can expose run history directly

## Rollout

Start with the lowest-risk recurring job (a read-only reporting job) to validate the leader-election behavior under real deploys, before moving settlement-critical jobs onto it.
