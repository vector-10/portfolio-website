<Section label="01 · Context and constraints">

The lender disbursed loans to customers' bank accounts through two payment providers. Payouts were fired straight from the API request, retried by a cron job, and reconciled against provider reports in a spreadsheet each morning.

<KeyValues items={[
  ["Volume", "~40k payouts a day, 3× on salary days"],
  ["Providers", "Two, with different APIs, rate limits and webhook reliability"],
  ["Downtime", "None allowed. Loans disburse 24/7"],
  ["Team", "3 engineers, 5 months, existing NestJS monolith"],
]} />

</Section>

<Section label="02 · Architecture">

<Diagram caption="Every payout is a ledger row first. Nothing reaches a provider unless it's committed, and nothing is marked paid unless the provider confirms it.">
  <Row>
    <Box>Loan service</Box>
    <Arrow>→ POST /payouts</Arrow>
    <Box sub="NestJS">Payout API</Box>
    <Arrow>→ one txn</Arrow>
    <Box sub="PostgreSQL" primary>Ledger + outbox</Box>
  </Row>
  <Arrow indent>↓ outbox relay</Arrow>
  <Row>
    <Box sub="Kafka, keyed by payout_id">payouts topic</Box>
    <Arrow>→</Arrow>
    <Box sub="Go · per-provider rate limit">Dispatch workers</Box>
    <Arrow>→</Arrow>
    <Stack>
      <Box external>Provider A</Box>
      <Box external>Provider B</Box>
    </Stack>
  </Row>
  <Arrow indent>↑ webhooks + status polling</Arrow>
  <Row>
    <Box sub="verify, dedupe, ack fast">Webhook ingest</Box>
    <Arrow>→</Arrow>
    <Box sub="hourly + end of day">Reconciler</Box>
    <Arrow>→ writes back to ledger</Arrow>
  </Row>
</Diagram>

1. The API writes the payout and an outbox event in one Postgres transaction. If the request dies, nothing is half-done.
2. A relay publishes outbox rows to Kafka, keyed by payout ID so one payout is never handled by two workers at once.
3. Go workers dispatch to providers under per-provider rate limits and fall back to the other provider on sustained errors.
4. Webhooks and status polling update the ledger. The reconciler compares ledger and provider reports hourly and flags any mismatch.

</Section>

<Section label="03 · Decisions and trade-offs">

<Decision title="Transactional outbox over publishing straight to Kafka" chose="Outbox table + relay" rejected="Dual write from the API">
Dual writes can commit to the database and fail to publish, or the reverse. The outbox adds about 200ms of delivery delay, which is invisible next to bank settlement times.
</Decision>

<Decision title="Kafka over BullMQ for dispatch" chose="Kafka, partitioned by payout ID" rejected="BullMQ on Redis">
We needed replay after incidents and strict per-payout ordering. BullMQ is simpler and we kept it for notifications, but Redis persistence was a risk for money movement.
</Decision>

<Decision title="Optimistic locking over distributed locks" chose="Version check in the UPDATE" rejected="Redis lock per payout">
The database is already the source of truth. A lock in a second system adds a failure mode without adding safety.
</Decision>

<Snippet label="The state transition that prevents double payment">

```sql
UPDATE payouts
   SET status = 'dispatched', attempt = attempt + 1
 WHERE id = $1
   AND status IN ('pending', 'retryable')
   AND attempt = $2          -- optimistic lock
RETURNING provider_ref;      -- 0 rows = someone else owns it
```

</Snippet>

</Section>

<Section label="04 · What went wrong">

Two weeks after launch, Provider B started returning timeouts for payouts that had actually succeeded. Our workers marked them retryable, and the optimistic lock stopped a second dispatch, but 212 payouts sat in limbo for six hours until the reconciler caught up.

The fix was to treat a timeout as *unknown*, not failed, and query the provider's status endpoint before any retry. If I did it again, I'd model "unknown" as a first-class state from day one and alert on how long payouts stay in it.

</Section>
